- **2026-08-01, CORRECTED same day** (Story 003): the entry directly above originally stated "`assert()` halts only the current call stack, not the process." **That was incomplete and led to a real bug that shipped past two rounds of self-review before `/code-review` caught it.** The corrected, empirically-verified finding: `assert(false, msg)` in Godot 4.7.1 aborts the rest of the **current function frame** when it fires — no statement textually after it in that function executes, including a `return`. A **value-typed** return (`Vector2i`, `int`, `bool`, ...) silently yields that type's zero-default when the frame aborts (harmless-looking, easy to miss); an **Object-typed** return (any `RefCounted`/`Node`-based class, including this story's own `TransformedFootprint`) yields `null`, which crashes the caller the moment it dereferences the result. This is why `get_transformed_cells()`'s illegal-rotation guard uses `push_error()` only — never `assert()` — while returning its `TransformedFootprint` result: `assert()` followed by `return result` in the same frame would make the `return` unreachable dead code. `_transform_cell()`'s own `assert(false)` fallback (its return type is `Vector2i`, a value type) is safe by the same logic and is kept as defense-in-depth, though it is unreachable via the only current public call path. **Action item**: audit `declared_bounds()`'s two debug asserts — both precede a `Vector2i` return, so they're safe under this corrected understanding, but this should be a conscious re-check (not an assumption) for any future story that adds an `assert()` ahead of an Object-typed return — grep the codebase for `assert(` followed by a `return` of a `RefCounted`/`Node`-typed value before trusting any new one — tracked from `production/epics/grid-system/story-003-grid-rotation-transform.md`
