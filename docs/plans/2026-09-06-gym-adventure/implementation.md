## P0：先修会污染新玩法的基础问题

1. 明确保存equipment_id、稳定asset_id与实例关系；新会话重建Placement、Selection及主场景resolver，禁止按footprint猜设备类型。
2. 保存Satisfaction的use-start拥堵快照；在动态拥堵和正在锻炼的成员上验证连续运行与读档一致。
3. 完整资源清单校验：当前data/expansion.json仅在工作区存在，新模式不用扩建也不能掩盖旧构建缺资源。分别定义两个模式的依赖；缺必要资源须非零退出。
4. 将主场景存读档、热图、Inspect和拒绝提示串联；测试真实事件次序和输入release，不只手调内部方法。
5. 定位场景重建时的RefCounted互相引用和连接清理；连续新建／销毁会话观察残留变化。原来的退出告警仅作为线索，不预设根因。

## 拟议模块与状态所有者

下表是实施候选。保留SimulationOrchestrator为唯一会话组装与生命周期所有者，main只承载场景和表现装配；禁止继续往多个位置散落创建模拟对象。

| 模块 | 唯一拥有的状态 | 依赖与输出 |
|---|---|---|
| DayCycleSystem | mode_id、day_id、phase、phase_tick、今日名册 | 读配置，向MemberSim／Course提交排程，发阶段事件 |
| CourseSystem | class_instance_id、绑定设备、分组、训练块、训练量、指导分值 | 借用MemberSim任务／预约接口，发member_course_completed |
| CoachSystem | 主角逻辑位置、请求ID、状态快照、选择和操作进度 | 输入桥提供命令；发一次指导结果 |
| OutingSystem | 正式尝试、体力、配速、路径段、计时与首次成绩 | 独立场景表现，读取同一全局tick与暂停规则 |
| RelationshipSystem | npc_id、永久事件集合、故事状态与每日反馈 | 消费去重事件，输出可用对话／包场条件 |
| Economy | 现金与已结算交易键 | 普通／课程两个入口由同一记账服务验证互斥 |
| GridSystem＋实例记录扩展 | equipment_id、asset_id、instance_id、朝向、等级、ownership、placed/stored | 先立ADR确定记录归属，不在多个UI映射中另存真相 |
| SaveLoad | 存档版本／模式与协调流程 | 每个系统提交自己的字段，整体validate后commit |

新增模块可以先放在很小的文件中；不为只有一种活动的OutingSystem搭建通用开放世界框架。普通访问与课程访问共享寻路和动作任务，不让两个控制器同时移动同一会员。

## 事件顺序与存档

新模式保持现有模拟子序列MemberSim→Congestion→Satisfaction→Economy；外围明确加入：

1. 处理本tick输入命令和模式门控；Outing／Coach操作在其合法阶段推进。
2. DayCycle生成到时排程；Course设置这一tick任务和预约。
3. MemberSim执行移动／训练并产生带tick、visit_id的事实事件；Congestion计算。
4. Course累积训练与到站事实，Satisfaction读取需要的状态；质量与满意度各自计算，不能互相覆写输入。
5. Economy消费事实事件，验证billing_type与唯一交易键；不在MemberSim发signal的瞬间绕过本阶段立即入账。
6. Relationship与目标消费已提交事实；DayCycle最后检查是否关门。
7. tick_count递增、发tick_completed；处理保存请求。

这是对ADR-0005 tick／信号契约的拟议扩展，实施前需修订该ADR和派发顺序测试；旧沙盒继续原序列。事件队列存有确定顺序，不跨tick遗留已消费事件。

保存完整性至少覆盖：课程预约与训练量、收费身份／已计费键、挑战路径小段起时／已记分集合、互动快照及操作时间、人物永久事件、借用／自有／收纳资产、use-start拥堵快照。加载UI从状态重新绑定，不重发业务奖励。

## 自动验收与人工验收

自动：GDD的费用边界、课程时序、预约互斥、晚到训练量、事件去重、暂停、存档、输入优先级、资源清单；必须至少一组测试使用真实main场景组装。

人工：人物动作与器械接触、昼夜可读性、键鼠操作、热图／Inspect、超时提示、画面遮挡、音效和首日教学。不能用读取源码字符串出现某方法代替实际操作验证。

性能目标：在记录型号／分辨率／渲染器的目标macOS机器和一台Windows机器上，12位访客＋主角＋固定NPC场景运行10分钟，目标帧耗时p95≤16.6ms；这是尚未测量的预算。发布平台未完成实测时单独标为未验证。

保存应在正常目标机器上完成后给成功提示，失败可见且保留上一份可用文件。资源回收以连续20次进入／退出会话后的对象与内存趋势评估，不能只观察一次进程退出。

## 外部试玩表

5位未玩过项目的玩家，每位记录首日开店时间、是否需要口头帮助、何时主动指导、是否理解布局因果、是否继续第二天。目标至少4位独立开班、3位指出一处布局影响；报告实际人数和原因，不用测试断言数替代体验结论。

观察信号：若主动指导几乎无人用，优先改动作反馈和决策可读性；若外出被普遍跳过，强化人物／当晚课程的关联；若布局与课程质量无差异，先调走路／准备时窗并复测；若玩家一直忙于菜单，减少面板和低价值请求。每轮只改变一个主要变量。
