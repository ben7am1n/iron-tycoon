重要：测试套件对环境写入敏感，会伪装成失败

首次在受沙箱限制的环境下运行时，套件报出 16 项失败（TOTAL: 6733 passed / 16 failed），涉及 file_io_version_test.gd（12）、first_day_playable_test.gd（3）、main_entry_process_test.gd（1）。
逐条核查失败信息后确认，全部是同一原因：SaveLoad: failed to replace save ... (error 1) —— 存档被写入操作系统用户目录 ~/Library/Application Support/Godot/app_userdata/GymManager/saves/，而该路径被沙箱拒绝写入。
把 HOME 指向临时目录后重跑，结果 6761 passed / 0 failed / EXIT=0。结论：代码是绿的，那 16 项失败是环境假阳性。

由此暴露的一个真实工程问题

SaveLoad 的落盘路径硬编码在 OS 用户数据目录下，任何受限环境（沙箱、无家目录的容器、CI 中未挂载的 HOME）都会让存档类测试失败。CI 目前跑在 ubuntu 上恰好有可写的 HOME，所以问题被掩盖了。建议给测试提供一个可注入的存档根目录，让套件与运行环境解耦。

六、需要留意的三处一致性风险

1 · 单一事实来源正在失效

本仓库同时存在四套进度表述：PROGRESS.md、production/epics/index.md、sprint-status.yaml、各 story/EPIC 文件。四者在 Audio、GA-001/002、GDD #13/#14/#15 上互相矛盾。当前靠人工交叉比对才能还原真相，建议明确以 story 文件为唯一权威并让其余三处自动派生。

2 · 178 个 worktree 会制造虚假的「进行中」

本次分析中，23 个「未合并分支」一度看起来像是待收编的工作，实际逐条比对后确认绝大多数早已落地。这类噪声会随 worktree 数量增长而放大，建议把 worktree 清理纳入常规流程。

3 · 「所有动作验收已通过」的表述仍需证据

09-09 复评曾明确记录：四 tick 上机过渡并非覆盖所有使用场景、锚点存在不等于四朝向接触全通过、部分录像为自动化业务命令而非真实输入。09-10 的提交声称已修复并交付验收图，但尚未见到独立复评确认。建议在试玩前安排一次针对性复核，避免把未验证的结论带入玩家测试。
